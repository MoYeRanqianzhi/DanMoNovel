**决定**：三站统一使用 React Router v8 的框架模式（用户 2026-09-27 在 React Router、Next.js、TanStack Start 三个选项中选定）。

**用户的要求**：框架此前一直没有定下；耽墨是商业站，需要合适的框架来做好缓存优化与搜索引擎优化；要先定框架，避免后续大规模改动。作者站也属于大量用户使用的站点，同样需要 SEO 等优化（同日补充）。

**用法**
- 小说站：服务端渲染，并支持流式输出。书页、榜单、分类、作者页必须在服务端输出正文 HTML，因为百度官方说它的爬虫只能读懂文本。每个路由用 `headers` 输出以 `s-maxage` 为准的缓存头。服务端渲染出的页面对所有访客都相同，书架、进度等个人数据在浏览器里补上，这样页面才能被 CDN 缓存。
- 作者站：与小说站一样用服务端渲染。公开页面（作者招募、福利政策、写作指南、征文活动、公告等）输出正文 HTML，并由 CDN 缓存；登录后的工作台（书房、作品管理、写作、数据）因人而异，缓存头用 `private, no-store`，不进 CDN。
- 管理站：只给内部工作人员使用，不需要 SEO。用 SPA 模式（`ssr:false`）构建成静态文件，由 Go 服务直接提供，运行时不需要 Node。
- Tauri 客户端：小说站的同一套代码以 SPA 模式构建成静态包。SPA 模式下路由不能导出服务端 `loader`、`headers`、`action`，数据要走 `clientLoader`。
- 部署：Go 服务是唯一对外的入口（见 [[backend-language]]、[[multi-site-deployment]]），小说站与作者站的页面请求转给只在内部网络中的 Node 渲染进程。
- 每个页面都要有真实的地址，可以分享、收录和直接打开。

**Why:**
- React Router v8 兼容原型所用的 Vite 8，服务端渲染、预渲染、SPA 三种模式用同一套工具链，每个路由都能直接输出 CDN 缓存头，还能构建出 Tauri 需要的静态包。
- Next.js 被排除：Tauri 只能用静态导出，而静态导出不支持没有预先生成的动态路由，也不支持 Server Actions（书与章节的 ID 由用户产生）；多实例自托管要自己接共享缓存并统一加密密钥；它不能用 Vite；缓存 API 在大版本之间变动频繁。
- TanStack Start 被排除：官方仍标注 RC。旧方案的教训之一就是不依赖预览版。
- Astro 被排除：交互组件要逐个声明才能跨页保留，不适合跨页 3D 书与阅读器。
- 放弃的是 Next.js 内置的 ISR 与数据缓存，以及更大的生态。缓存改由标准 HTTP 头、CDN 与 Go 服务端的 Redis 承担。

**How to apply:**
- 路由模块遵循 React Router v8 的约定。React 19 起推荐在组件里直接写 `<title>`、`<meta>`。RSC 仍是实验性的，不要依赖。
- 有两件事要尽早做小规模验证（PoC），结果写回本条：
  1. 同一套小说站代码同时产出服务端渲染构建与 SPA 构建（可以在 `routes.ts` 里按构建目标选择不同的路由模块）。
  2. 默认用 `isbot` 识别爬虫，要确认它能否认出 360、神马、头条的爬虫，认不出就换成自己维护的名单。
  3. 一个 Node 进程同时加载小说站与作者站两份服务端构建，各自监听一个内部端口。
- 框架、SEO 与国内 CDN 的事实及出处见 [[web-framework-facts]]。

**Evidence:** 用户 2026-09-27 原话："实际上框架一直没有定下了，这种商业站需要合适的框架，才能有足够的缓存优化、搜索优化等"与"先定框架，避免后续大规模改动"；同日在选项中选择"React Router v8（推荐）"；随后补充："注意：作者站也需要SEO等优化，也属于大量用户使用的站点"。

**Recheck when:** 两项 PoC 有了结果；React Router 发布新的大版本；Tauri 或鸿蒙的限制让 SPA 构建不可行时。
