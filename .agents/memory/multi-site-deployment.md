**用户的要求（2026-09-27）**
- 除了小说站，还要有作者站和管理站，三站使用相同的设计风格。
- 三站将来部署在不同域名上，可以设计成"一套部署暴露多个端口"之类的形式。
- 管理站在原型阶段先不设计具体功能，主要完成视觉验收。

**方案（我的判断）**
- 部署：一个服务端程序（一个部署单元）监听三个可配置的端口，每个端口对应一个站点，提供该站的静态前端和该站的接口。反向代理把各个域名映射到对应端口，并负责 TLS。
- 三站是三个不同的源（origin）。这不只是部署形式，也带来安全上的收益：
  - Cookie 与本地存储按源隔离，小说站即使出现脚本注入，也读不到作者站、管理站的会话。会话 Cookie 使用 `HttpOnly`、`Secure`、`SameSite=Strict` 与 `__Host-` 前缀。
  - 管理站的端口可以只绑定内网或 VPN。
  - 各站单独构建，公开的小说站包里不含作者站、管理站的代码；各站可以设置各自的 CSP。
  - 服务端校验请求来源（Origin），管理接口只接受来自管理站的请求。
- 账号：全站只有一套账号，但每个站有各自的会话。作者站通过认证服务跳转，沿用读者的登录；管理站要求重新验证身份并启用两步验证，会话有效期更短。
- 设计系统：三站共用设计令牌、8 套主题、Book3D、飞行引擎与基础组件。建议各站默认主题不同，让工作人员一眼分清自己在哪个站：小说站用薛涛笺，作者站用缃叶，管理站用墨白。8 套主题在各站都可以选。
- 原型用"一个进程起三个开发服务器、各占一个端口"来模拟这种部署，端口与目录见 .agents/docs/prototype.md。

**Why:** 分域名部署与统一风格是用户的明确要求。按源隔离让最敏感的管理会话与公开站点天然分开；分开构建则避免后台界面随公开站点一起发布出去。

**How to apply:** 写新代码前先判断它属于某个站点还是共享层；共享层不得依赖任何站点的代码。跨站链接使用可配置的站点地址，不要写死端口或域名。身份与权限规则见 [[staff-roles]]，布局要求见 [[responsive-layouts]]。

**Evidence:** 用户 2026-09-27 原话："除了小说站，还需要做使用相同设计风格（但是注意到时候会部署在不同域名，比如可以设计为一套部署暴露多端口之类的）的作者站、管理站……管理站可以先不设计具体功能，因为当前属于原型阶段，主要是完成视觉验收"。

**Recheck when:** 开始设计服务端或部署方案时；用户对域名、端口、账号体系提出具体要求时。
